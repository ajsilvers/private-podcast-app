## Release blockers and material risks

1. **No complete signup-to-email path.** Add durable enrollment and delivery states, automatic retries and a visible repair path. Only allowlisted opt-in offers grant a show; a newsletter signup must not accidentally enroll in every podcast.
2. **Drip releases at server-local midnight.** [feed-generator.ts:44](/Users/main/Work/code/private-podcast/src/lib/feed-generator.ts:44) truncates both dates. Under UTC, signup at 23:50 makes episode 2 eligible at 00:10, only 20 minutes later. Under the local Podgorica timezone that same pair is not eligible. The schedule is runtime-dependent. Confirmed by AJ in this review: exact elapsed intervals from captured signup time, not calendar-day boundaries.
3. **Binge dates can be in the future and change when publication changes.** [line 70](/Users/main/Work/code/private-podcast/src/lib/feed-generator.ts:70) subtracts an episode number from the count of published episodes. With only episode 3 published and a September 17 start, UTC output is September 19. Use stable first-publication dates and serial ordering instead of the old count-based backdating.
4. **Malformed/nonstandard RSS.** [line 94](/Users/main/Work/code/private-podcast/src/lib/feed-generator.ts:94) emits `itunes:type=complete`; use serial or episodic independently of drip/binge. Description CDATA breaks on `]]>`; enclosure URLs are not XML-escaped; channel lacks `link`. Upload accepts formats beyond MP3 while enclosure MIME is always MPEG. Restrict launch audio to MP3, validate metadata and parse generated XML in tests. Apple's [ordering guidance](https://podcasters.apple.com/support/3143-how-to-set-the-order-of-podcast-episodes) distinguishes serial and episodic presentation.
5. **Retry and revocation semantics.** Subscriber lookup followed by create can race; email is neither trimmed nor lowercased here. Duplicate requests after revocation automatically reactivate and reset start time, unlike dashboard reactivation. Delayed retries must never undo revocation. Malformed JSON currently becomes 500. [Subscriber API](/Users/main/Work/code/private-podcast/src/app/api/v1/shows/[showId]/subscribers/route.ts:39).
6. **Production auth and input safety.** [auth.ts:8](/Users/main/Work/code/private-podcast/src/lib/auth.ts:8) falls back to a known session secret. Remove that fallback and fail closed. Middleware checks cookie presence rather than session validity and broadly exempts dotted paths; dashboard layout and mutation handlers do perform session checks, so cookie presence alone is not proof of a complete auth bypass. Verify authorization directly wherever secrets/data are read, especially settings; add login and public opt-in abuse controls. Show/episode PATCH lack schemas; partial updates clear some omitted values. [Show PATCH](/Users/main/Work/code/private-podcast/src/app/api/shows/[id]/route.ts:58), [episode PATCH](/Users/main/Work/code/private-podcast/src/app/api/episodes/[id]/route.ts:5).
7. **Schedule stability.** Episode deletion renumbers remaining episodes; changing feed type or interval affects all subscribers. Freeze sequencing/settings once enrollment starts for launch, permit unpublish and append-only episodes, and use a new show/version for a different cadence. Do not retroactively change subscribers' schedules by editing a live show.
8. **Analytics on critical path.** Feed logging and activation updates are awaited before RSS, so their failure returns 500. Make them best effort with bounded waits. First feed fetch is not proof of listening: email security scanners and validators can request URLs. [Feed route:25](/Users/main/Work/code/private-podcast/src/app/api/feeds/[token]/route.ts:25).
9. **Infrastructure not proven.** Build configuration must regenerate Prisma; database region/pooling and migrations need deliberate setup. R2 CORS currently names localhost only. No live database schema, content inventory, DNS, sender, bucket or account plan was verified.

Private here means an unguessable bearer feed URL. Audio URLs are public in the current R2 design. Revoking a feed prevents future RSS retrieval, not playback of audio already downloaded or copied. This matches a free opt-in feed model; strict media authorization would be a separate project.

## Hosting decision

| Platform | Fit | Decision |
| --- | --- | --- |
| Vercel | Direct Next.js support; application has short database/API requests, direct object-store uploads and dynamic RSS. Scheduled bounded queue processing is sufficient. | Recommended. Use a commercial plan; Hobby is limited to personal non-commercial use. Keep app region near Neon. |
| Netlify | Supports App Router/route handlers through OpenNext; both source websites already use Netlify Functions/Blobs. | Viable fallback if account consolidation or existing plan capacity is preferable. Requires verifying adapter, Prisma runtime and caching behavior. No website migration needed either way. |
| Railway | Suitable for Next.js and persistent worker/database services. | Prefer only if workload grows to require a persistent queue worker or hosting all backend services together. No such requirement is evidenced today. |

Sources checked 17 September 2026: [Vercel Next.js](https://vercel.com/docs/frameworks/full-stack/nextjs), [Vercel Hobby scope](https://vercel.com/docs/plans/hobby), [Netlify Next.js](https://docs.netlify.com/build/frameworks/framework-setup-guides/nextjs/overview/), [Railway full-stack Next.js](https://docs.railway.com/guides/fullstack-nextjs). Recommendation is an architectural judgment, not a measured performance/cost comparison. Account entitlements and incremental spend are unknown; do not describe the deployment as free.

Use a stable HTTPS feed hostname before sending real subscriptions. `feeds.donebythree.com` is a proposed example, not an approved/configured domain. A single hostname can serve both brands. R2 production audio needs a custom domain or an already verified CDN: Cloudflare explicitly reserves `r2.dev` for non-production use ([R2 docs](https://developers.cloudflare.com/r2/buckets/public-buckets/)). Preserve `/api/feeds/{token}` permanently once issued.

Drip feed eligibility is evaluated on feed requests. **No scheduled publishing job is required for drip.** Scheduled jobs in the plan are for enrollment retries, email delivery and health/retention. A listener's app decides when to poll; server eligibility time is not an instant-device-delivery guarantee.

## Review verification and limits

- `./node_modules/.bin/tsc --noEmit --incremental false`: passed using installed dependencies and existing generated Prisma client. This is not a clean-install or production-build result.
- `npm run lint`: failed with 9 errors and 12 warnings. Eight errors are `require()` imports in `.claude/helpers`; one is dashboard `<a>` navigation. Scope lint appropriately and fix the application error without editing unrelated harness tooling.
- In-memory transpilation of the existing feed generator with synthetic objects reproduced the UTC midnight and binge future-date defects; generated output also demonstrated raw `&` in enclosure attributes and broken `]]>` CDATA. No database was accessed by these probes.
- Compared document hashes, Git histories, current source, graph cards, schemas and configuration. Inspected outer archive DOCX content and prompting sequence; no credentials printed or copied.
- No production build, dependency installation/audit, database query/migration, real upload, email, provider API call, browser integration test or deployment ran. Those are named acceptance gates in the schedule.
- Existing uncommitted changes at review start: modified `AGENTS.md`, modified `README.md`, untracked `CLAUDE.md`. Preserve them. Local `.env`, `.next` and `node_modules` are not evidence of a working production deployment.
